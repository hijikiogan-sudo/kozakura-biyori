## 調査した現状

バックアップの書き出し・旧v1/現v2の検証・確認付き復元・最終操作日時・オフライン対応は実装済みだった。ただし、写真と動画の件数がまとめられ、日時が補助文字に埋もれていた。復元確認は文章中心で、現在の内容とファイル内の内容を比較しにくかった。確認中に別画面で保存された変更を検出する仕組みもなかった。

お世話通知は保存した予定からICSを作る方式で、登録・通知許可をアプリから確認できない。説明と設定・書き出しの操作が分かれており、順序を整理する余地があった。メニューは全項目を一列に表示していた。

## 復元の安全策と互換性

ファイル全体を読み込み、既存の `M.validateBackup` と既存の容量制限で検証してから比較画面を開く。不正なJSON・不正な項目・対応外のアプリ/形式・容量超過は復元せずに拒否する。検証とプレビューだけではIndexedDBを変更しない。

キャンセル・Esc・保存エラー・確認中のデータ変更では復元しない。書き込みは既存の原子的なread-modify-writeトランザクションを利用する。比較で了承された内容から現在のデータが変わった場合は、その変更を上書きしない。確認の間に進むタイマーの表示更新は保存データを変えないため、実際の保存変更とは区別される。

従来どおり、復元を実行すると現在のデータをファイルの内容に置き換え、タイマーと最終書き出し日時は復元しない。旧形式にない表紙設定・イラスト・アクション設定等は、既存の正規化により初期値を使う。保存値の新設や移行処理の変更は行わない。

バックアップファイルは従来の `app: kozakura-biyori`、`version: 2`、`exportedAt`、`data` のJSON。v1/v2の受け入れを維持する。DB名 `kozakura-biyori-local-v1`、DBバージョン1、公開URL、写真/動画形式・保存上限、健康の保存値とグラフ、日付ごとの集計は変えていない。`model.js` と `platform.js` は未変更。

## 通知とプライバシー

予定保存だけでは、閉じている間の通知を予約しない。ファイル作成・保存とカレンダーへの追加も別操作である。登録完了・通知許可・通知音はアプリから検出できず、「登録済み」等の完了表示は追加しない。音量・消音・集中モードはiPhone側の設定に従う。

カレンダー側の予定は、アプリ内の実施・変更・停止と自動同期しない。写真や飼育記録を外部へ送信せず、新しい通知サーバー・クラウドDB・外部APIは導入しない。カレンダーへの追加後に行われる同期は、そのカレンダーの設定に従う。

## iPhone実機で必要な確認と次の対象

Safariとホーム画面PWAで、実際の共有画面から「ファイル」へ保存できること、保存したJSONを再選択できること、比較画面のスクロール・キャンセル・文字拡大を確認する。実データで復元テストを強制せず、まず予備端末や合成データで確認する。クラウドのChromium検証を実機検証とは呼ばない。

ICSの取り込み、予定の通知、通知許可・消音・集中モード、変更/停止後のカレンダー側削除と重複回避は実機での確認が必要。保存中のOS強制終了を防いだり、ファイルの保存完了や通知音を保証したりはしない。

健康の新しい保存値・グラフ軸文字、複数羽、課金、App Store公開、ネイティブ通知は今回の範囲に含めない。写真を主役にしたホーム・写真サイズ・放鳥ボタンの位置と今日の合計・しぐさ設定は維持する。
